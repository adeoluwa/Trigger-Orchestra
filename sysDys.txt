1. OVERVIEW
────────────────────────────────────────────────────────────────────────────────

Trigger Orchestra is a deployment orchestration platform that lets developers
push code from GitHub repositories to cloud platforms (Railway, Render) through
a single dashboard. The system is configured by a `trigger.yml` file in the
repo root that defines environments, branches, and target platforms.

High-level components:

  ┌─────────────────────────────────────────────────────────────────────────┐
  │                         Client Layer                                    │
  │   Next.js 16 (React 19, App Router, Tailwind v4, shadcn/ui, SWR)       │
  │   apps/web/  ─────────────────────────────────────────  :3001           │
  └────────────────────────────┬────────────────────────────────────────────┘
                               │  REST / JSON  (Bearer JWT)
  ┌────────────────────────────▼────────────────────────────────────────────┐
  │                         API Layer                                       │
  │   Express (TypeScript), Hexagonal Architecture, Zod validation         │
  │   Trigger/  ──────────────────────────────────────────  :3000           │
  └──┬──────────┬───────────┬───────────┬────────────────────────────────── ┘
     │          │           │           │
  PostgreSQL  Redis      GitHub       Railway / Render
  (TypeORM)  (BullMQ +  (OAuth +      (Deployment
             Locks)      REST API)     providers)

3. BACKEND ARCHITECTURE
────────────────────────────────────────────────────────────────────────────────

3.1 DESIGN PATTERN — HEXAGONAL ARCHITECTURE (PORTS & ADAPTERS)
───────────────────────────────────────────────────────────────

Each domain module follows the same three-layer structure:

  Domain Layer (Core)
  │   - Pure interfaces (ports) — no external dependencies
  │   - Business entities (plain TypeScript interfaces)
  │   - Domain errors (extend AppError)
  │
  Application Layer (Use Cases)
  │   - Service classes consume only domain ports
  │   - Business logic lives here exclusively
  │   - Validated by Zod DTOs before entering the service
  │
  Adapter Layer (External Contracts)
      Inbound:  HTTP controllers + routes (Express)
                Queue consumer (BullMQ worker)
      Outbound: TypeORM repositories
                Platform providers (Railway, Render)
                OAuth/GitHub API service
                JWT token service
                Encryption utilities

This means: the service doesn't know about HTTP, TypeORM, or BullMQ —
it only knows about the port interfaces injected at startup.

3.2 DEPENDENCY INJECTION
────────────────────────

There is no IoC container. Each module exports a factory function that
manually wires up all dependencies:

  createAuthModule(dataSource)       → { router }
  createProjectModule(dataSource)    → { router }
  createDeploymentModule(dataSource, queue) → { router }
  createSecretModule(dataSource)     → { router }

These factories are called once in infra/server/routes.ts at startup.
The deployment worker (deployment.consumer.ts) builds its own service
instance with the same pattern.

3.3 STARTUP SEQUENCE
─────────────────────

  main.ts
    1. Validate all env vars (Zod schema — process.exit(1) on failure)
    2. AppDataSource.initialize() — run TypeORM migrations, open DB pool
    3. getRedis()                 — open ioredis connection, test connectivity
    4. createExpressApp()         — Helmet, CORS, rate-limit, JSON body parser
    5. registerRoutes(app)        — mount all module routers under /api/v1
    6. mountBullBoard(app)        — mount Bull Board at /admin/queues
    7. mountSwagger(app)          — mount Swagger UI at /api/docs
    8. app.listen(PORT)
    9. startDeploymentWorker()    — start BullMQ consumer (concurrency: 3)

4.1 AUTH MODULE
───────────────

  Responsibility: user identity, credentials, OAuth, GitHub API access

  Files:

    domain/errors/AuthErrors.ts           — EmailAlreadyExistError, InvalidCredentialsError
    domain/ports/index.ts                 — AuthRepository, TokenService, GitHubOAuthPort

    application/services/auth.service.ts  — Core use cases (see below)
    application/dtos/index.ts             — RegisterUserSchema, LoginUserSchema, RefreshTokenSchema

    adapters/outbound/entities/UserRepository.ts      — TypeORM: users table
    adapters/outbound/jwt/JwtTokenService.ts          — signs/verifies access + refresh tokens
    adapters/outbound/oauth/GitHubOAuthService.ts     — GitHub OAuth + REST API
    adapters/inbound/http/auth.controller.ts          — HTTP handler methods
    adapters/inbound/http/auth.routes.ts              — Express route definitions
    auth.module.ts                                    — DI factory

  Use Cases (auth.service.ts):
    register(dto)          — hash password, save user, issue tokens
    login(dto)             — verify password, issue tokens (rotate refresh)
    githubLogin(code)      — exchange OAuth code, upsert user, issue tokens
    getProfile(userId)     — fetch name + githubUsername from DB
    refresh(dto)           — rotate refresh token (detect reuse attacks)
    getGithubRepos(userId) — fetch user's repos via stored GitHub token
    createRepoConfig(...)  — push trigger.yml to GitHub via Contents API

  Token Strategy:
    Access token  — JWT HS256, 7d TTL, payload: { id, email }
    Refresh token — JWT HS256, 30d TTL, payload: { sub: userId }
    Both stored in DB; refresh token rotated on every use.
    Reuse detected: if stored token != presented token → invalidate + throw.

  GitHub OAuth Flow:
    Browser → GET /auth/github         (redirects to GitHub authorization page)
    GitHub  → GET /auth/github/callback?code=...
    Server:   exchange code for token, upsert user, redirect to:
              {FRONTEND_URL}/auth/callback?token=...&refreshToken=...
    Frontend: parse URL params, save to localStorage, call /auth/me, go to /dashboard

  HTTP Endpoints:
    POST   /api/v1/auth/register
    POST   /api/v1/auth/login
    POST   /api/v1/auth/refresh
    GET    /api/v1/auth/me                         [auth required]
    GET    /api/v1/auth/github                     → redirects to GitHub
    GET    /api/v1/auth/github/callback            → redirects to frontend
    GET    /api/v1/auth/github/repos               [auth required]
    POST   /api/v1/auth/github/repos/:owner/:repo/config  [auth required]

4.3 DEPLOYMENT MODULE
─────────────────────

  Responsibility: deploy execution, async job processing, rollback, log streaming

  Files:
    domain/entities/Deployment.ts     — Deployment, DeploymentLog interfaces
    domain/errors/DeploymentErrors.ts — NotFound, AccessDenied, AlreadyRunning, CannotCancel
    domain/ports/index.ts             — DeploymentRepository, DeploymentProviderPort,
                                        DeploymentProviderFactory

    application/services/deployment.service.ts  — Core use cases
    application/dto/index.ts                     — TriggerDeploymentSchema

    adapters/outbound/DeploymentProviderFactoryImpl.ts       — factory: platform → provider
    adapters/outbound/railway/RailwayDeploymentProvider.ts   — Railway GraphQL adapter
    adapters/outbound/render/RenderDeploymentProvider.ts     — Render REST adapter
    adapters/outbound/repository/DeploymentRepository.ts     — TypeORM
    adapters/inbound/http/deployment.controller.ts
    adapters/inbound/http/deployment.routes.ts
    adapters/inbound/queue/deployment.consumer.ts            — BullMQ worker
    deployment.module.ts

  Use Cases:
    triggerDeployment(dto, userId)
      1. Validate environment + project ownership
      2. Acquire Redis lock (SETNX, 720s TTL) → 409 if already locked
      3. Fetch latest commit SHA from GitHub
      4. Save deployment record (status: queued)
      5. Set environment status → deploying
      6. Enqueue BullMQ job (jobId = deploymentId for deduplication)
      7. Return deployment record

    processDeployment(jobData)   [runs inside BullMQ worker]
      1. Fetch deployment + environment records
      2. Update status: queued → building
      3. Resolve secrets for environment (decrypt)
      4. Call provider.deploy() → platformDeploymentId
      5. Update status → deploying
      6. provider.streamLogs() — poll platform every 5s, append to DB
      7. provider.getStatus() — get final outcome
      8. On SUCCESS: complete(success), env → deployed, release lock
      9. On FAILURE:
           a. complete(failed)
           b. findLastSuccessful(environmentId)
           c. If found: provider.rollback(lastPlatformId, lastCommitSha, env)
              - stream rollback logs
              - poll rollback status
              - env → deployed (success) or failed
           d. If not found: env → failed
      10. finally: release lock (always)

    cancelDeployment(id, userId)
      - Validate, call provider.cancel(), complete(failed), release lock

    getLogs(id, userId)          — fetch all logs for a deployment (sorted by timestamp)
    listByProject(projectId)     — all deployments for a project
    getDeployment(id, userId)    — single deployment with access check

  Deployment Status State Machine:
    queued → building → deploying → success
                                  → failed → (rollback) → deploying → success
                                                                     → failed

  Platform Providers — Common Interface (DeploymentProviderPort):
    deploy(environment, commitSha, envVars)  → platformDeploymentId
    rollback(lastPlatformId, lastCommitSha, environment) → platformDeploymentId
    getStatus(platformDeploymentId, environment) → DeploymentStatus
    streamLogs(platformDeploymentId, environment, onLog) → void (polls)
    cancel(platformDeploymentId, environment) → void

  Railway Provider (GraphQL):
    deploy:    serviceInstanceRedeploy or serviceCreate mutation
    rollback:  deploymentRedeploy(id) — re-runs exact historical build
    status:    deployment(id) query → maps BUILDING/DEPLOYING/SUCCESS/FAILED
    logs:      deployment(id) { logs } query — polled every 5s, up to 120 polls
    cancel:    deploymentCancel(id) mutation
    env vars:  variableCollectionUpsert mutation (before deploy)

  Render Provider (REST):
    deploy:    POST /services/:id/deploys  (or POST /services for new service)
    rollback:  POST /services/:id/deploys with { commitId: lastCommitSha }
    status:    GET  /deploys/:id → maps live/failed/build_in_progress
    logs:      GET  /services/:id/logs?deployId=...  — polled every 5s
    cancel:    POST /deploys/:id/cancel
    env vars:  PUT  /services/:id/env-vars (before deploy)

  HTTP Endpoints:
    POST   /api/v1/deployments                    [auth required]
    GET    /api/v1/deployments/:id                [auth required]
    DELETE /api/v1/deployments/:id                [auth required]
    GET    /api/v1/deployments/:id/logs           [auth required]
    GET    /api/v1/deployments/:id/logs/stream    [SSE, auth required]

5.3 REDIS (infra/cache/ + infra/lock/)
───────────────────────────────────────

  redis.config.ts:
    Singleton ioredis client (getRedis())
    Used by: DeploymentLock, Bull Board health check
    Retry strategy: exponential backoff, max 10 retries, cap at 3s

  DeploymentLock (infra/lock/DeploymentLock.ts):
    Purpose: prevent concurrent deployments to the same environment
    Mechanism: SET lock:deploy:{environmentId} 1 EX 720 NX
      - Returns true (acquired) or false (already locked)
      - TTL 720s = 12 min (matches max log-stream window)
      - Acquired in HTTP handler (triggerDeployment)
      - Released in worker finally block (processDeployment)
      - Also released by cancelDeployment

5.4 BULLMQ QUEUES (infra/queue/)
──────────────────────────────────

  bullmq.config.ts:
    Connection: raw { host, port, password } options passed to BullMQ
    (avoids ioredis version type mismatch — BullMQ manages its own client)

  Queues:
  ┌───────────────────┬─────────┬─────────────────────────────────────────┐
  │ Queue             │ Retries │ Notes                                   │
  ├───────────────────┼─────────┼─────────────────────────────────────────┤
  │ deployment        │ 3       │ exponential backoff (5s base)           │
  │                   │         │ keep 100 completed, 200 failed          │
  ├───────────────────┼─────────┼─────────────────────────────────────────┤
  │ notification      │ 5       │ exponential backoff (2s base)           │
  │                   │         │ keep 50 completed, 200 failed           │
  └───────────────────┴─────────┴─────────────────────────────────────────┘

  Worker settings (createWorker):
    concurrency: 3     — max 3 deployments processed simultaneously
    limiter: { max: 10, duration: 5000 }  — max 10 job starts per 5s window
                                            (backpressure guard for burst traffic)

  Job schema (DeploymentJobData):
    { deploymentId, environmentId, projectId, platform: 'railway' | 'render' }

  Job names:
    PROCESS_DEPLOYMENT  — main worker path
    CANCEL_DEPLOYMENT   — defined but dispatched via HTTP cancel endpoint

    Global Express error handler:
    - AppError instances → structured JSON with statusCode

11. RELIABILITY MECHANISMS
────────────────────────────────────────────────────────────────────────────────

11.1 IDEMPOTENCY / RACE-CONDITION PREVENTION
────────────────────────────────────────────

  Problem: two concurrent HTTP requests for the same environment would both
  pass the status check and create two deployments.

  Solution: Redis SETNX lock in triggerDeployment()
    Key:  lock:deploy:{environmentId}
    TTL:  720 seconds (12 minutes)
    Flow: acquire → proceed OR reject with 409 DEPLOYMENT_ALREADY_RUNNING
    Release: always in worker processDeployment() finally block

  This makes the lock span two separate system boundaries (HTTP handler →
  worker), which is safe because TTL handles crash recovery automatically.

11.2 ATOMIC ROLLBACK
─────────────────────

  Triggered automatically when processDeployment() detects final status = failed.

  Algorithm:
    1. Query findLastSuccessful(environmentId) → most recent status='success' row
    2. If none: mark env failed, log "no rollback candidate"
    3. If found:
       a. Call provider.rollback(lastPlatformDeploymentId, lastCommitSha, env)
       b. Set env → deploying (rollback in flight)
       c. Stream rollback logs (same log record, source='platform')
       d. Poll status until terminal
       e. Set env → deployed (success) or failed

  The original failed deployment record stays as-is (status='failed').
  Rollback actions appear as additional log entries within the same deployment.

11.3 BACKPRESSURE
──────────────────

  BullMQ Worker limiter: { max: 10, duration: 5000 }
    - At most 10 jobs start per 5-second window across all workers
    - Surplus jobs wait in the queue (Redis-backed, durable)

  Worker concurrency: 3
    - At most 3 deployments processed in parallel

  BullMQ retry: 3 attempts, exponential backoff starting at 5s
    - Handles transient failures (network blip, API timeout)

11.4 RELIABILITY TEST SCRIPT (scripts/load-test.ts)
─────────────────────────────────────────────────────

  Test 1 — Idempotency:
    Fire 50 concurrent POST /deployments/trigger to same environment.
    Pass condition: exactly 1 accepted (201), 49 rejected (409).

  Test 2 — Backpressure:
    50 requests round-robined across N environments.
    Pass condition: N accepted (one per env), remainder 409.
    Observe queue depth at /admin/queues.

  Test 3 — Rollback (manual):
    Inject BUILD_SHOULD_FAIL=true as a secret, trigger deploy,
    observe log sequence showing automatic rollback to last good commit.

  Usage:
    API_URL=http://localhost:3000/api/v1 \
    ACCESS_TOKEN=<jwt> \
    PROJECT_ID=<uuid> \
    ENVIRONMENT_ID=<uuid> \
    npx ts-node Trigger/scripts/load-test.ts [1|2|3|all]

12. DATA FLOW — END-TO-END DEPLOY
────────────────────────────────────────────────────────────────────────────────

  User clicks "Deploy" in the dashboard
       │
       ▼
  POST /api/v1/deployments  { projectId, environmentId }
       │
       ▼
  auth.guard.ts — verify JWT, attach { id, email } to req
       │
       ▼
  DeploymentController.trigger()
       │
       ▼
  DeploymentService.triggerDeployment()
    ├─ find environment (DB)
    ├─ find project + check ownership (DB)
    ├─ acquire Redis lock (SETNX) ──────────── 409 if locked
    ├─ find user GitHub token (DB)
    ├─ fetch latest commit SHA (GitHub API)
    ├─ save deployment record status=queued (DB)
    ├─ set environment status=deploying (DB)
    └─ enqueue BullMQ job { deploymentId, environmentId, ... }
       │
       ▼  (async — HTTP returns 201 with deployment record)
  BullMQ worker picks up job
       │
       ▼
  DeploymentService.processDeployment()
    ├─ status → building
    ├─ resolve + decrypt secrets (DB)
    ├─ provider.deploy()             → Railway GraphQL / Render REST
    ├─ status → deploying
    ├─ provider.streamLogs()         → polls platform every 5s, appends to DB
    ├─ provider.getStatus()          → final outcome
    │
    ├─ SUCCESS path:
    │    complete(success), env → deployed, release lock
    │
    └─ FAILURE path:
         complete(failed)
         findLastSuccessful() → if found:
           provider.rollback() → new platformDeploymentId
           set env → deploying
           streamLogs (rollback)
           getStatus (rollback)
           env → deployed | failed
         release lock (always, via finally)
       │
       ▼
  Frontend polls GET /deployments/:id/logs every 2s (SWR)
  UI updates status badge and appends log lines in real time
